# MelonHub 面向对象设计答辩

以下以当前三层按业务分包与 RBAC1 实现为准。图和源码入口见 [后端 UML 与代码导读](后端UML与代码导读.md)。回答时应先说具体责任分配，再指出代码；类名或包名本身不能证明符合某个设计原则。

## 1. 结构化设计与 DDD 有何不同？

MelonHub 在一个 Spring Boot 工程里提供两种可选实现。控制器（`api/<biz>`）依赖 `service/port/<biz>` 的 13 个用例接口，启动时按 `melonhub.backend-strategy` 选择 `structured` 或 `ddd`；它们使用同一数据库、HTTP 契约及共享基础设施。

| 比较点 | 结构化实现 | DDD 实现 |
| --- | --- | --- |
| 分解依据 | 以业务用例的步骤组织过程，服务串联读取、校验和写入 | 将部分业务状态与规则封装到领域模型，由应用服务协调事务和外部交互 |
| 管理员创建 | `StructuredAuthService` 调用静态 `StructuredAdminHierarchyProcedures`，节点与角色功能作为参数输入 | `DddAuthService` 构造持有节点和角色功能的 `AdminHierarchy`，调用 `validateCreate` |
| 范围判断 | 过程遍历记录及集合 | `AdminScope` 封装部门/软件范围，提供包含关系判断 |
| API 权限查询 | 服务查询操作映射、展开 RBAC1 角色继承权限并判断集合包含 | 静态目录负责操作映射，账号模型判断权限，服务通过仓储端口读取数据 |
| 持久化依赖 | 服务直接依赖 `infrastructure.persistence.repository` Spring Data JPA 仓储 | 应用服务依赖 `service.ddd.domain.repository` 领域仓储端口，由 `infrastructure.persistence.gateway` 的 `Jpa*Adapter` 直接桥接至 JPA 仓储（无 DAO 中间层） |
| 并发一致性 | 服务事务、统一锁序与 JPA 悲观锁配合过程校验 | 同样需要服务事务与仓储锁；领域对象负责内存中的规则判断 |
| 测试重点 | Controller 层真实数据库双策略契约测试、底层并发/缓存/哈希链测试 | 领域规则纯单测、应用编排、适配器与双策略同契约回归 |

结构化设计也可以用 Java 类和接口，也可以做到低耦合；DDD 也包含过程编排。区别主要是业务规则由谁持有、怎样组织状态与行为，不能用“有没有类”或“分了几层”区分。这里展示的是已有代码中的 DDD 分层实践，不宣称已完整实施战略 DDD，也不宣称所有应用服务都很薄：`DddDomainRbacService` 等仍包含较多编排与校验。

## 2. 哪些是真正的值对象、领域模型和工具？

| 当前类型 | 可以据代码说明的性质 | 不应夸大的说法 |
| --- | --- | --- |
| [AdminScope](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/value/AdminScope.java) | 不可变 record，构造时复制集合；按内容比较，封装范围包含关系，是值对象的直接示例 | 不因有一组字段就把所有 DTO 称作值对象 |
| [AdminHierarchy](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/model/AdminHierarchy.java) | 持有节点、子节点索引和角色功能，检查树结构与授权不变量；可解释为以管理员层级为范围的一致性模型 | 代码注释称“聚合根”，但完整树的读锁和事务在外围；它不是独立持久化实体，也不能单独保证并发一致性 |
| [IdentityAccountAggregate](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/model/IdentityAccountAggregate.java) | 持有身份、角色和权限快照并提供判断方法 | 名字含 Aggregate 不等于具备完整聚合生命周期、持久化和所有权设计 |
| [CoursePermissionCatalog](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/value/CoursePermissionCatalog.java) | 静态操作映射目录及查询方法 | 它没有实例值语义，不能称为值对象 |
| [PasswordPolicy](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/value/PasswordPolicy.java) | 静态密码规则工具 | 规则工具不是密码值对象 |
| [SystemStatusReport](../backend/src/main/java/com/melonhub/rbac/service/ddd/domain/model/SystemStatusReport.java) | 静态状态结果组装函数 | 不因位于 model 包就称为聚合根 |

因此，材料不再把 `model` 包的 12 个类统称为“12 个聚合根”，也不把 `value` 包全部称为值对象。聚合是业务一致性边界和对象所有权设计，不能按文件数计算。

## 3. 创建管理员 API 体现哪些 GRASP 原则？

**Information Expert（信息专家）**：`AdminHierarchy` 拥有父子节点和角色功能，负责 `validateCreate` / `validateUpdate` / `violations`；`AdminScope` 拥有部门和软件集合，负责 `coversDepartmentsOf` / `coversApplicationsOf`。判断交给掌握所需信息的对象，而不是让控制器复制规则。

**High Cohesion（高内聚）**：层级与范围规则分别集中在上述两个模型。`DddAuthService` 负责用例流程，但仍包含前置校验和审计描述，不能说“所有规则都已从应用服务移出”。

**Low Coupling（低耦合）和 Indirection（中介）**：`DddAuthService` 使用 `AdminAccountRepositoryPort`，实际由 `JpaAdminAccountRepositoryAdapter` 委托 `AdminAccountRepository` 与 `AdminSessionRepository`。更换存储实现时，可以保留领域模型及端口契约；仍需保证锁语义和事务行为，接口本身不会自动保证替换正确。

具体链路：`AccountController.create → AuthUseCase.createAccount → DddAuthService → AdminHierarchy.validateCreate → AdminAccountRepositoryPort`。禁止越界时，在写账号前抛出领域异常，由 `DddBoundary` 转为 HTTP 层使用的异常；事务回滚。

## 4. API 权限查询与双策略体现哪些 GRASP 原则？

**Controller（控制器）**：`IdentityController.apiPermission` 接受系统事件、读取协议参数并委托 `IdentityUseCase`。它不直接查询数据库或复制权限判定逻辑。GRASP Controller 是责任分配概念，不能只凭类带 `@RestController` 注解就认定实现合理。

**Polymorphism（多态）和 Protected Variations（受保护变化）**：`StructuredIdentityService` 与 `DddIdentityService` 实现同一 `IdentityUseCase`。HTTP 调用方保持同一契约，启动配置选择实现。变化被隔离在接口后，但新增功能时仍须维护两套实现并执行回归。

**Information Expert（信息专家）**：DDD 查询中，`IdentityAccountAggregate.hasUiPermission` 持有当前权限集合，所以可负责权限包含判断。这个 API 的领域逻辑较简单，主要差异在责任位置和基础设施隔离；管理员层级 API 更适合展示复杂领域约束。

**Pure Fabrication（纯虚构）**：仓储适配器（`infrastructure.persistence.gateway.Jpa*Adapter`）不是业务世界中的实体，而是为了存储职责和降低耦合设计的软件对象。无需为了凑齐全部 GRASP 原则，为每个 API 强行附会所有原则。

## 5. 怎样说明两套实现的验证程度？

- [R33_ArchitectureBoundaryUnitTest](../backend/src/test/java/com/melonhub/rbac/architecture/R33_ArchitectureBoundaryUnitTest.java) 检查源码依赖边界；它不能证明领域建模质量或所有运行行为。
- [R33_BackendStrategyWiringUnitTest](../backend/src/test/java/com/melonhub/rbac/architecture/R33_BackendStrategyWiringUnitTest.java) 检查两种配置下全部 13 个用例端口的排他装配。
- [R33_DddDomainAndDualStrategyParityUnitTest](../backend/src/test/java/com/melonhub/rbac/architecture/R33_DddDomainAndDualStrategyParityUnitTest.java) 与 [R19_AdminTreeUnitTest](../backend/src/test/java/com/melonhub/rbac/r19/R19_AdminTreeUnitTest.java) 检查选定领域规则和同输入的决策。
- 全部 27 项业务功能（R1–R34）均配备从 Controller 层发起 HTTP 请求并在真实 MySQL 测试库上分别以 `structured` 和 `ddd` 运行的双策略集成测试，55 个核心接口另有双策略 JSON 契约锁 [R31_ApiContractIntegrationTest](../backend/src/test/java/com/melonhub/rbac/r31/R31_ApiContractIntegrationTest.java) / [R31_ApiContractDddIntegrationTest](../backend/src/test/java/com/melonhub/rbac/r31/R31_ApiContractDddIntegrationTest.java)；完整执行范围见 [需求与测试矩阵](requirements.md#5-需求与测试代码对照矩阵) 和 [验证记录](验证记录.md)。

答辩可以说：“我们以同一 HTTP 契约、55 个核心接口 JSON 契约锁和 27 组双策略 Controller 真实数据库回归场景约束两套实现，在已执行场景中结果一致；源码边界和 13 端口装配另有自动检查。”
